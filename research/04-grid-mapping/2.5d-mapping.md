# 2.5D Mapping Representations

## Definition
2.5D maps collapse the full 3D structure into a 2D lattice (e.g. BEV grid or polar grid) where each cell stores a **vertical summary**:
- max/min elevation (height),
- occupancy/evidence Stack (observed free / occupied),
- optionally: vertical range, variance, or per-height-zone histogram.

"2.5D" = we trade full 3D voxel detail for a cheap per-cell elevation statistic. Enough for terrain drivability; fast to build/update.

## Common 2.5D variants
| Variant | Cell layout | Stores | Use case |
|---------|-------------|--------|----------|
| Digital Elevation Map (DEM) / Terrain grid | Uniform BEV | height / elevation certainty | Terrain drivability |
| Occupancy grid (+ height) | Uniform BEV | obstacle (free/occupied) + height | Nav costmap w/ height floor |
| Multi-level elevation (MLS) | Uniform BEV | per-height-layer occupancy | Multi-storey / complex collisions |
| Polar grid | Rings (r,θ) | height + occupancy | Foveated natural fit (our PS) |
| Variable-resolution grid (foveated) | Non-uniform | height + semantic + dynamics | OUR target |

## Why Elevation-over-Voxel
- Beam ray-casting assigns each scan to a line; ML constructions (OctoMap, 3D hashing) are 3D → cost scales with volume, and vertical zones are wasteful for ground robots/vehicles.
- Elevation map inherently tells you **drivability** (slope field around) at the cost of occlusions/tunnels (rare on roads).

## Terrain / Slope from 2.5D
- From per-cell DEM heights, compute finite-difference gradients → slope + convexity.
- Drivable if: |slope| < threshold AND elevation diff vs neighbors < clearance.
- Refine with RANSAC plane fits or elevation-map based ground fitting (see terrain-analysis.md).

## Our PS Reinterpretation ("2.5D semantic elevation grid")
Each cell carries:
- `elevation` (per-cell z statistic, e.g. min/mean-of-ground),
- `obstacle_height` (max z above ground → clearance),
- `semantic` (dominant class: road/terrain/vegetation/building/pole/vehicle/pedestrian...),
- `dynamics`  (static/dynamic confidence from temporal persistence),
- `resolution` (cell size, adaptive),
- optional `uncertainty`.

Single-pass accumulation from segmented point cloud → grid update → publish.

## Stored State vs Derived Features (2026-09-16)

**STORED STATE (persistent per-cell fields, canonical):**
- `elevation`
- `obstacle_height`
- `semantic_distribution`
- `dynamic_state`
- `resolution`
- `uncertainty`
- `seen_timestamp`

**DERIVED FEATURES (computed reactively for the selective SVM; NOT all stored as fields):**
- geometric/elevation, semantic, spatial/sensor, temporal, uncertainty feature candidates — full list in `07-benchmarking/svm-refinement-study.md` §5.
- The `feature_builder` derives the feature vector on demand (e.g., for gated cells), rather than persisting every candidate as a cell field. Not every candidate feature is a stored field.

## Fit / Trade-offs for Our PS
- PRO: cheap, direct drivability output → DRDO-friendly.
- CON: loses multi-storey structure; occlusions (underground/overpass) degrade.
- CON: semantics+height in one 2.5D cell requires careful "which points vote" logic (ground vs obstacle vs tree canopy).
